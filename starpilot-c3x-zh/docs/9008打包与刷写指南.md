# 9008 刷机包：打包与刷写指南

> 把一台 C3X 的完整系统做成 9008 可刷包，用于变砖恢复或多设备统一部署。
> 本文档全部内容来自 2026-11-18 在 `comma-5e0dca10` 上的实测。

| 项目 | 结论 |
|---|---|
| 能否做包 | ✅ 可以，产出 84 项 / 29.13 GiB 的包 |

## 二、为什么不用 EDL 读取（实测记录）

工具自带 `Firehose.read()`，理论上能读分区。实测结果：

| 尝试 | 分块 | 超时 | 结果 |
|---|---|---|---|
| 1 | 8 MiB | 60 s | 8 MiB 只收到 5 MiB，超时 |
| 2 | 2 MiB | 60 s | 收到 2,064,478 / 2,097,152 字节后停顿 |
| 3 | 2 MiB | 60 s | 重试导致协议错位（`Firehose XML 无效`）|
| 4 | 1 MiB | 180 s | 第 2 块就卡死 |
| 5 | — | — | 端口停在 Firehose，Sahara 不响应 |

**根因**：

1. 链路吞吐只有 ~1.4 MB/s（USB 全速级别），读 29 GiB 需 6 小时
2. 传输中会**停顿**，任一块超时即整盘失败
3. **不能重试** —— 超时后设备可能仍在发数据，残留字节会让下一条命令解析失败

SkyGMFlasher 作者也是因此把"写后回读"整个删掉了（README：「0.1.4 取消写后回读」）。

**每次失败的会话还会把设备留在 Firehose 状态，必须物理拔插 USB 才能重新握手。**

## 三、SSH 打包流程（推荐）

### 前提

- 设备**正常开机**（不是 9008），能 SSH
- PC 上有 Python 3 + `pip`
- 手边有一个已登记 Firehose 的包（用于取 `prog_firehose_ddr.elf`）
- 磁盘剩余 ≥ 32 GiB

### 3.1 准备环境

```powershell
# 安装依赖（只有 SSH 方案需要，纯标准库 + 无 pyserial）
python -m pip install pyserial

# SkyGMFlasher 源码（用于 GPT 解析与最终校验）
#   从 SkyGMFlasher 发布包的 source.zip 解出，或直接用 source/ 目录
```

### 3.2 探测（只读，约 30 秒）

```powershell
python tools\build_package_ssh.py `
  --ssh comma@192.168.1.12 `
  --ssh-key "$env:USERPROFILE\.ssh\id_ed25519_comma" `
  --out D:\c3x_pkg `
  --flasher-source "D:\SkyGMFlasher\source" `
  --firehose-from "D:\已有包" `
  --dry-run
```

输出会列出 6 个 LUN 的完整分区表和总写入量。**确认无误再做下一步。**

### 3.3 正式导出（约 27 分钟 @18 MB/s）

```powershell
python tools\build_package_ssh.py `
  --ssh comma@192.168.1.12 `
  --ssh-key "$env:USERPROFILE\.ssh\id_ed25519_comma" `
  --out D:\c3x_pkg `
  --flasher-source "D:\SkyGMFlasher\source" `
  --firehose-from "D:\已有包" `
  --split-mb 0 `
  --yes
```

参数说明：

| 参数 | 建议值 | 说明 |
|---|---|---|
| `--split-mb` | `0` | 不切分。切分会增加 dd 的 skip/count 复杂度，实测无必要 |
| `--zero` | `logdump,rawdump` | 这两个是纯日志分区，写全零可省 3.45 GiB |
| `--skip` | `""`（空） | **不要跳过 userdata** —— 校验器要求每个分区都有镜像 |

脚本会自动：

1. 通过 SSH 读 6 个 LUN 的容量（`/sys/class/block/sd?/size`）与主/备 GPT（`dd`）
2. 用工具的 `gpt_pair()` 解析分区表
3. 逐分区 `dd` 流式传输到 PC（**只读**）
4. `userdata` 写 64 KiB 复位标记
5. `logdump`/`rawdump` 写全零
6. 生成 `raw_plan.json` / `SHA256SUMS.txt` / `rawprogram0-5.xml` / `patch0-5.xml`
7. 调用 `load_plan()` 自校验

### 3.4 如果校验失败

常见原因与修法：

| 报错 | 原因 | 修法 |
|---|---|---|
| `program/GPT/镜像清单不一致` | 某个分区没导出（如跳过了 userdata）| `python tools\repair_package.py` |
| `整分区长度或哈希错误` | 零填充分区的 `expanded_sha256` 记错 | 同上（会以 `files` 为准重算）|
| `'prog_firehose_ddr.elf'` KeyError | `files` 清单里没登记引导文件 | 同上（自动复制并登记）|

`repair_package.py` 会补全 userdata、修正哈希、登记 Firehose，然后重新校验。

## 四、包结构

```
c3x_pkg/
├── raw_plan.json          65 KB   包清单（luns / images / programs / files）
├── SHA256SUMS.txt        6.7 KB   每个文件的哈希
├── prog_firehose_ddr.elf 678 KB   引导（哈希须等于工具登记的 9e7226d2…）
├── userdata.img           64 KB   COMMA_RESET + 零填充
├── rawprogram0-5.xml              每个 LUN 的写入指令
├── patch0-5.xml                   空（本包不需要 patch）
├── gpt_main0-5.bin / gpt_backup0-5.bin
├── system_a.img / system_b.img    各 11.58 GiB
├── boot_a.img / boot_b.img        各 64 MiB
├── modem_a/b, dsp_a/b, tz_a/b, ... （LUN4 共 48 个）
└── logdump.img / rawdump.img      全零
```

写入项 **84** = 71 个分区 + 12 个 GPT（6 主 + 6 备）+ 1 个 userdata。

## 五、刷写流程

### 5.1 让目标设备进 9008

```bash
# 若设备能开机：
sudo sh -c 'echo 1 > /sys/module/msm_poweroff/parameters/download_mode'
sudo reboot
```

之后 USB 枚举为 `05c6:9008`（`Qualcomm HS-USB QDLoader 9008 (COMx)`）。

### 5.2 刷写

1. 运行 `SkyGMFlasher.exe`（**必须保留 `_internal` 目录**）
2. 选择包目录 `D:\c3x_pkg`，等待校验结束（约 1-3 分钟）
3. 选 COM 口 → **连接设备**
4. **全选 84 项**
5. 勾选 **重建分区表**
6. 点 **刷写** → 确认
7. 等待完成（29 GiB，USB 2.0 约 2-3 小时；USB 3.0 约 40-60 分钟）
8. 完成后手动点 **重启**

⚠️ 全程保持供电，不要拔线、不要关工具。

### 5.3 首次开机

- 包里的 `userdata` 只有 64 KiB 标记，没有文件系统
- `comma.sh` 会检测到 `/data` 未挂载 → 自动 `reset --recover`
- 自动格式化并创建 `/data`（几十秒，比 RC10 的 dm-crypt 方案快得多）
- 首启会把 `/usr/comma/setup_keys` 写成 `GithubSshKeys`，**SSH 默认可用**

### 5.4 部署 StarPilot + 汉化

```bash
scp -r starpilot-c3x-zh comma@<设备IP>:/tmp/
ssh comma@<设备IP>
sudo bash /tmp/starpilot-c3x-zh/provision.sh
```

`provision.sh` 会 clone StarPilot、装依赖、建 acados、写 `continue.sh`、设语言、装汉化补丁。

## 六、已踩过的坑

### 1. 设备卡在 Firehose，Sahara 不响应

**现象**：端口还在 COMx，但 `Sahara 1/6：接收超时`。

**原因**：上一次会话已把 Firehose 加载到 RAM，设备不再发 Sahara HELLO。

**修法**：物理拔插 USB（等 3 秒再插）。软件 `power reset` 不能可靠恢复。

### 2. EDL 读超时后重试会污染协议

超时后设备可能仍在发数据，残留字节进入缓冲区 → 下一条命令返回的是垃圾。

**修法**：不要在同一会话内重试大块读取。要么整盘重来，要么改用 SSH。

### 3. `fix_degenerate_lun0()` 不能用于读设备

那个函数是给**写包**用的：修复 RC10 那种「system_b 被删空、只剩类型 GUID」的单槽布局。

双槽设备的 entry 7 是真实分区，调用会 `AssertionError: unexpected GPT entry 7`。

**修法**：读路径先用设备原始 GPT 解析，失败才做最小修复（备份头 CRC → 退化布局）。

### 4. 输出目录非空检查太晚

读几何时就会把 GPT 文件写进输出目录，之后再做「目录必须为空」检查会自己拦住自己。

**修法**：检查放在连接设备之前。

### 5. XML 属性类型必须是字符串

`raw_verify` 用 `dict(xml_attrib)` 与 `programs` 清单做**直接相等比较**，XML 读回全是字符串。

**修法**：清单里所有值都存 `str`。

### 6. 切分模式下 dd 必须带 skip/count

`dd if=/dev/disk/by-partlabel/system_a` 不加限制会**读整个分区**，切 12 段就读 12 遍（进度会超过 100%）。

**修法**：`--split-mb 0` 不切分，或给每段加 `skip`/`count`。

### 7. 零填充分区忘了设 digest

零填充分支如果不设置 `digest` 变量，会沿用上一个分区的哈希 → `整分区长度或哈希错误`。

**修法**：`repair_package.py` 以 `files` 为准重算。
